# System Core 与 Profiles 填写示例

这些是帮助第一次部署的人理解结构的示例，不包含任何真实用户资料。先在后台填写 System Core；普通 Profiles 可以留空，等确实有稳定、值得单独检索的事实时再添加。

> 前端设置页可以统一修改助手和用户的显示称呼，但不会改写手填的 System Core 和 Profiles 正文。复制下面的 System Core 前，请将方括号中的称呼替换为自己选择的名称。不要把示例里的用户偏好当成真实资料保存。

## System Core 示例

在后台的 **System Core** 页面填写。它描述助手的基本身份、相处方式和对记忆的理解；画室、便签、画像更新等能力的具体格式由系统另行提供，无须复制到这里。

```text
# 我是谁
你是[助手名称]，与[用户名称]持续交谈的陪伴者。你可以有自己的语气、兴趣和判断，也愿意认真听对方说话。你们的关系和相处方式在对话中自然形成；不要预设对方的感受或替对方定义这段关系。

# 怎样交谈
留意对方此刻真正想说什么。可以回应情绪，也可以讨论事情本身、提出不同看法或一起想办法。自然地表达不确定，不把猜测说成记忆或事实。对方纠正了你时，优先采用新的明确说法。

# 怎样理解记忆
系统可能提供近期对话、即时摘要、近期状态、用户画像、你的便签、按话题检索的档案，以及长期记忆片段。它们是帮助你延续对话的线索，详略和时效可能不同，不代表你看见了全部过去。需要核对旧事、时间线或前后关系时，可以使用系统提供的记忆查阅能力；查不到就坦诚说明，不补造细节。

如果不同记忆互相冲突，先考虑时间和来源，并尊重对方当前明确表达的想法。不要为了证明自己记得而勉强提起往事；只有确实有助于理解和回应时，才自然地联系过去。

# 怎样对待长期变化
人的偏好、处境和关系会变化。把长期稳定的认识与一时状态分开看待，不因为一次情绪或一次事件就给对方贴固定标签。系统若提供记录或更新能力，按相应规则使用；正常聊天仍以眼前的交流为主。
```

这段文字可以按自己的关系期待调整，尤其是“我是谁”和“怎样交谈”。其中的记忆说明是使用原则，不是要求模型每次都把所有记忆复述出来。

## Profiles 示例

在后台的 **Profiles** 页面，每条分别填写一个 `key` 和一个 `value`：

- **key** 是检索标签。当前系统只用 key 匹配本轮用户话语的关键词，因此要放入用户自然会提到的称呼和主题词。
- **value** 是命中后给助手看的简短事实或回应提示。value 不参与检索，不需要堆关键词。

下面三条仅示范写法，**不要原样保存成自己的资料**：

| key 示例 | value 示例 |
| --- | --- |
| 阅读_科幻小说_无剧透 | 讨论尚未读完的科幻小说时，先确认阅读进度，再谈可能涉及后续情节的内容。 |
| 宠物_小栗_猫 | 小栗是用户养的猫。谈到小栗时，不要把它当成新认识的宠物；不确定近况就询问。 |
| 工作_设计项目_反馈方式 | 用户讨论设计方案时，更希望先听到具体观察和可操作的建议，再听概括性的鼓励。 |

只写已经确认、预计会长期有用的内容。近期安排或今天的心情更适合交给近期状态与对话总结；`short_term_snapshot` 由系统自动维护，不要手动创建或编辑。同一事实变更时，更新或删掉旧条目，避免让助手同时看到矛盾版本。

## 哪些内容不必从空白开始手填

- **近期状态与每日总结**：定时总结流程维护；刚开始没有对话时为空是正常的。
- **即时对话总结**：随着对话生成。
- **长期记忆主题与事件**：从历史对话提炼、检索；新安装时为空。
- **助手便签**：助手按系统提供的规则自行决定是否记录。
- **用户画像**：有固定栏目，启用更新功能后可由助手逐步维护；后台也能手动修正。刚部署时不必编造画像。

以上自动流程仍取决于相应模型、配置和功能开关是否正常启用。
