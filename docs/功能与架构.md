# 功能与架构

这份文档介绍公开草稿里各模块怎样配合，方便读者决定从哪里开始看代码。M-Home 是情感陪伴类 AI 应用的实现参考：对话是入口，记忆让不同窗口之间的交流保持连续，共读、笔记和画室则承载具体活动。各项能力依赖所配置的模型及服务，并非安装后都会自动可用。

## 功能概览

| 模块 | 用户可以做什么 | 主要实现位置 |
| --- | --- | --- |
| 对话 | 创建和重命名对话、折叠历史对话；向上分段加载消息；搜索及查看当前对话的消息地图；发送图片、预览和编辑待发送图片；切换文段或气泡样式 | `frontend/src/App.tsx`、`gateway/main.py`、`gateway/chat_images.py` |
| 模型与设置 | 选择 API 账户和模型；按需开启联网搜索、思考、生图等能力；控制时间戳、用量和缓存信息的显示；设置助手与用户称呼 | `frontend/src/components/SettingsPanel.tsx`、`gateway/router.py`、`gateway/app_identity.py` |
| 记忆 | 按层注入设定与记忆；从对话提炼长期记忆；检索相关主题；让助手按需再查阅一次记忆 | `gateway/injector.py`、`gateway/summarizer.py`、`gateway/memory_recall.py` |
| 画室 | 使用候选图生成与审稿流程；在受支持的 OpenAI 主模型上使用同轮原生生图；在对话中查看作品和进度 | `gateway/art_generation.py`、`gateway/router.py`、`frontend/src/components/ArtJobStatus.tsx` |
| 共读 | 上传 EPUB、阅读章节、保存进度与批注，并在批注下继续交流 | `gateway/reading.py`、`frontend/src/components/BookReader.tsx` |
| 笔记 | 保存图文笔记与标签、搜索笔记、请求助手评论，并查看评论任务状态 | `gateway/notes.py`、`frontend/src/components/NotesView.tsx` |
| 后台 | 查看和编辑 System Core、Profiles、画像、记忆与摘要等内容，检查部分注入与写入结果 | `admin.html`、`gateway/main.py` |

其中一些按钮只是让模型或后端**可以**使用对应能力，并不保证每轮都会调用。画室使用哪条流程取决于主模型的服务类型；图片理解、总结和出图也可能需要各自的模型配置。

## 一轮对话怎样经过系统

1. 浏览器把用户消息和本轮开关交给网关；网关保存对话与图片，并按需准备图片理解结果。
2. 记忆模块组合固定设定、近期状态和检索到的内容，再由路由层把请求发送到选定的模型服务。
3. 模型回复以流式内容返回。思考、搜索、主动查阅记忆和生图等事件会转换为前端可显示的状态；内部使用的创作或记忆指令会单独处理。
4. 可见回复与相关用量、图片或任务状态保存后，刷新页面仍可从历史记录加载。

普通聊天记录、摘要和结构化记忆主要保存在 SQLite；上传的图片和电子书还涉及文件存储。浏览器设置与服务器保存的资料是两类数据：例如 API 账户保存在当前浏览器，称呼设置保存在服务器。公开草稿不包含任何真实使用数据。

## 记忆由哪些层组成

| 层 | 来源与作用 |
| --- | --- |
| System Core | 部署者在后台手动写入的核心设定。它是应用的基础说明，不会自动从聊天生成。 |
| Profiles | 部署者手动维护的 `key / value` 条目。检索只匹配 key；命中后才把对应 value 带入上下文，避免正文里的普通词造成误命中。 |
| 用户画像 | 按固定栏目维护对用户的长期认识。已填写的栏目会随主对话注入。 |
| 助手便签 | 助手主动写给未来自己的提醒。主对话默认读取最近 10 条。 |
| 近期状态 | 即时摘要、每日总结和短期快照帮助保留近期时间线。 |
| 长期记忆 | 从对话提炼为主题 Thread 与具体 Event；按关键词检索，可选用语义检索补充。当前用户消息的关键词优先，上一轮用户消息提供低优先级线索。 |

这些内容会按规则被动注入；如果查阅更多往事有助于当前回答，助手还可调用 `recall_memory`，按主题标识 `thread_key` 或查询词 `query` 查阅。每轮最多主动查阅一次。这个动作与一般关键词检索不同：它是模型在回复过程中自行发起的补充查询。

想了解初次应手填什么，可看 [System Core 与 Profiles 填写示例](填写示例.md)。示例只说明结构和写法，不会自动写入数据库。助手与用户的称呼可在前端设置中修改；已有聊天、Profiles 和手写 System Core 不会因此被改写。

### 用户画像与助手便签

**用户画像**有九个固定栏目，涵盖认知、价值、自我认识、情绪、关系和能力等方面。助手每轮主对话都能看到已有栏目。部署者启用 `PORTRAIT_UPDATES_ENABLED` 后，当一个稳定判断需要修正，或交流中出现了尚未记录的新维度，助手可以在本轮回复里提交一次更新。通常会重写相关栏目，把新旧内容合成一段并删掉过时判断，也可以在段尾追加一句确认性的补充。初次部署可以从空画像开始，完整画像可在后台用 `PORTRAIT_ADMIN_PASSWORD` 解锁查看和编辑。

**助手便签**存的是助手想带到下次交流里的提醒。助手会自行判断是否值得写，每轮最多一条，通常用第一人称简短记下一个结论，比如「聊到还没想清楚的决定时，我可以先问对方想从哪里说起」。适合记录反复出现的回应偏好、对关系的发现，或值得延续的陪伴方式。网关会检查近期的重复内容，之后按时间带入最新便签，主对话的条数由 `MAV_NOTES_LIMIT` 控制。

用户可以在「我们」页查看小本本，也可以在后台的备忘页查看、新增或删除便签。「我们」页的标题和说明会使用设置里的助手称呼。比如把默认的 Mav 改为小栀，页面会显示「小栀的小本本」和「小栀 写给未来自己的提醒」。

例如，一段交流反复体现出「对方常通过把不同选项说出来理清思路」，这个长期观察可以写进画像的「认知风格」。助手想留给自己的具体做法，可以写成上面的第一人称便签。共读批注和图文笔记评论也会读取已有画像和最近便签，供生成回复时参考。

两种写入都由主对话模型提交。网关会从聊天正文里剥离内部的 `<mav_portrait>` 或 `<mav_note>` 内容，验证并保存到 SQLite，写入成功后在对话里显示一条简短提示。维护规则分别在 [portrait.py](../gateway/portrait.py) 和 [internal_capabilities.py](../gateway/internal_capabilities.py)，解析与保存入口在 [main.py](../gateway/main.py)。

## 画室：从创作构想到选出作品

如果你喜欢用 Claude 等模型作为日常聊天的主模型，而当前接入方式没有原生生图，可以继续用熟悉的模型对话。打开画室后，助手根据交流决定要不要画、想表达什么，再把构想交给独立的生图服务。候选图出来后，助手还可以看图审稿、修改构想后重画，或决定是否把作品发给你。

### 候选图与审稿

这条路径适用于未走 OpenAI 原生生图的主模型。它把「想画什么」「生成像素」「要不要把作品交给用户」拆成几个步骤：

1. **提出构想**：主模型在正常回复的同时写一份隐藏的创作笺，包含完整 `prompt`、画幅比例、必须保留与明确避免的要素；也可以明确决定这轮不画。创作笺不显示给用户。若这一轮打开了画室、回复却没有留下可识别的决定，后端会再请求一次补写决定。
2. **生成候选图**：后端将创作笺交给配置的生图服务。默认一批生成 **3 张**；数量由 `ART_DRAFT_COUNT` 配置，代码上限为 6 张。候选图及缩略图先记录在画室任务里。
3. **让助手真实看图**：后端把这一批候选图、用户原始要求、创作笺和必要的局部对话交给审稿模型。Claude 主对话默认沿用本轮模型审稿；其他主模型使用配置的可看图审稿模型。这里是一次独立的模型请求，不是只按文字提示词猜测图片效果。
4. **选中、打回或不发表**：审稿可以选出一张并附上发表时想说的话；如果整批都有明显问题，可以说明主要原因并写出**完整的修订 prompt**，让后端再生成一批；最终仍不满意则可以拒绝发表。默认最多打回 **1 次**，因此最多审两批，次数由 `ART_MAX_RETRIES` 配置。最终批次只能选图或拒绝发表。
5. **交付作品**：选中的图片附到这轮助手消息，画室卡片显示结果；未选中的候选图不会作为作品公开。任务状态、候选图和选择结果会保存，刷新后仍可看到已完成的作品。

例如，第一批三张都把人物关系画错时，审稿结果会带着「人物站位不对」一类的原因及改好的完整 prompt 进入第二批。第二批不再无限重试；Mav 需要从中选一张，或者告诉用户这次没有画到愿意交付的程度。生成接口出错、审稿结果无法解析等技术失败则显示为任务失败，不等同于审稿主动拒绝。

这套设计让助手参与创作决定和成品选择，而生图服务负责输出像素；用户在对话里看到的是最终被选中的作品和必要的进度状态。

### OpenAI 同轮原生生图

当请求走受支持的 OpenAI 官方主模型时，主模型可以在本轮直接调用 `image_generation`：它自己决定何时落笔、怎样描述画面，结果与文字回复一起回到对话。**这一条没有隐藏创作笺，也不经过候选图审稿。** 通常生成 1 张；用户明确要求 2 张或 3 张时可按要求生成，最多 3 张。作品同样保存并附到当前消息，供以后重新打开对话查看。

两条流程共用对话中的作品展示，但模型调用方式、所需配置和任务状态不同。实际可用能力仍以所选模型与 API 服务为准。

## 共读：围绕书中的一句话继续聊

共读不是把整本书塞进一次聊天请求。它先把书整理成可逐章阅读的内容，再把批注锚定到原文位置：

1. **上传与准备**：用户上传 EPUB，系统解析书名、章节及正文并加入书架。后台逐章处理，长章节逐段累积摘要，等整章处理成功后一起保存摘要和批注。可以在书架查看进度。恢复处理时会跳过已完成的章节，旧书已经保存的摘要会保留。
2. **按阅读进度呈现**：阅读器显示章节正文、目录与批注位置，并保存上次阅读的章节和位置。批注是在对应原文旁出现的，不是脱离书本的一份整章评论。
3. **就地讨论**：用户也可以选中一段原文写自己的批注。Mav 的回复会结合附近原文、章节摘要和这条批注流式出现；对同一条批注继续回复时，讨论链会一并提供给模型，形成围绕这个位置的连续交流。

预处理后续章节时，模型看到的是当前正文、第一章及近期已读章节的摘要；提示要求它只从读到这里的视角写批注，避免后文视角进入前面的章节。阅读模块的模型服务需要另行配置，设置方式见[本地试运行](本地试运行.md)。

## 从哪里开始读代码

- `frontend/src/App.tsx`：主页面、对话列表、消息显示和输入交互。
- `frontend/src/components/`：设置、共读、笔记、图片编辑和画室状态等界面。
- `gateway/main.py`：网关入口、聊天请求、消息接口和后台接口。
- `gateway/router.py` 与 `gateway/formatter.py`：识别服务类型、整理请求与流式响应。
- `gateway/injector.py`、`gateway/memory_recall.py`、`gateway/summarizer.py`、`gateway/scheduler.py`：记忆注入、主动查阅与摘要。
- `gateway/db.py`：SQLite 表结构和数据读写。
- `gateway/reading.py`、`gateway/notes.py`、`gateway/art_generation.py`：三个活动模块的后端实现。

准备运行时看[本地试运行](本地试运行.md)。打算接入互联网时，先看[发布前检查](发布前检查.md)：前端演示口令不构成网关及后台的服务器端身份验证，需要按自己的部署环境补上访问保护。
